# 規格優先開發流程

使用者是這個流程的新手，要看得到每一步。**透明優先於速度**：中間產物都存成檔案，關卡都停下來等使用者說「繼續」。向使用者說明用白話，一次只講一步，術語要解釋。

## 角色

- 使用者：講需求、看過每個關卡、拍板
- Claude（Sonnet 5.5，advisor 設為 Opus 5.5）：討論、寫規格書、判斷審閱意見、審查程式碼。**不寫功能程式碼**
- Codex astra（`gpt-6-astra`）：只審閱規格書，唯讀
- Codex luna（`gpt-6-luna`，思考強度 `max`）：照規格書實作，只寫程式、不建置。任務 1 已實際跑過

## 已驗證的部分

### 1. 討論與規格書
- 先讀現有程式碼再寫，不憑空設計。用白話問問題，選擇題優先；方向不確定時畫草圖讓使用者選。
- **追問到沒有模糊地帶才停**：不是問一輪就動筆，每個設計決定（包含邊界案例、例外情況「如果 XX 發生呢」）都要有明確答案才算討論完。使用者答不出來或不在意的細節，由 Claude 自行判斷並在規格書寫明理由，不要卡住流程硬逼使用者決定。
- 使用者改變方向時，先改規格書（寫進變更紀錄），再談實作。
- 規格書放 `docs/specs/<功能名>.md`，必含：目標、非目標、設計細節、可客觀檢查的驗收條件、任務清單、風險、待確認事項。
  - 任務清單：每個任務小到一次能做完且能獨立驗收；每個任務**標出依賴關係**（這個任務要等哪個任務先完成、哪些任務彼此互不相干可任意順序做），讓實作順序在規格書階段就定好，不用等到交給 luna 時才臨時想。

### 2. astra 審閱
- 呼叫（唯讀，只能看不能改）：
  `codex exec -m gpt-6-astra -s read-only "<審閱提示>"`，或使用者自己互動執行 `codex -m gpt-6-astra -s read-only`。
- 優先在使用者的 Terminal 面板執行，讓使用者即時看到；不可用時用 Bash，並把完整輸出存檔。
- 審閱提示要包含：只審不改；對照實際程式碼；找「內部矛盾、與程式碼不符或做不到、遺漏邊界、驗收無法客觀檢查、任務太大」；標嚴重度。
- **複審必須附上前一輪紀錄檔**，否則 astra 無法逐項核對。
- 紀錄放 `docs/specs/reviews/<功能名>-roundN.md`：astra 原文（不刪改）加上 Claude 的判斷表（每點：接受／不接受、理由、處理）。

### 3. 討論與定案
- 向使用者呈現「astra 說了什麼／我怎麼判斷」，只有需要取捨的才問使用者；其餘自行判斷但必須講理由。使用者同意後才修規格書。
- 通常兩輪：astra 說可定案、或剩下的只有已處理的低嚴重度項目，即定案。

### 4. 踩過的坑
- Codex 版本太舊時，新模型會報「需要更新版本」。用 `codex update` 升級（先問使用者）。
- 專案由 `project.yml` 產生，專案檔未進 git；新增 Swift 檔只要重新 `xcodegen generate`（見第 7 節）。
- App 最低支援 iOS 17、本機為 Xcode 26：iOS 26 的 API（如 Liquid Glass）必須用 `#available(iOS 26, *)` 包起來並提供舊版退回。
- `docs/specs/reviews/` 與規格書只存檔，不必每次都 commit；commit 前先問使用者。

## 已驗證的部分（2026-10-07 起）

### 5. 請 luna 實作
- 一次一個任務；先確認 git 狀態乾淨（上一個任務已 commit），方便審查與丟棄。
- 實際跑過的指令（任務 1 成功）：
  `codex exec -m gpt-6-luna -c 'model_reasoning_effort="max"' -s workspace-write "<任務指令>"`
- 任務指令要寫明：只做哪個任務、先讀哪些檔、只准改哪些檔、不准做什麼、**先怎麼驗證（測試或明確的檢查方式）再寫實作**、結束時回報什麼。**任務指令與規格書的版本、狀態必須一致**（規格書標頭要寫「定案」才能開跑）。
- **luna 的環境沒有網路、也沒有模擬器 runtime，無法建置或執行 App**；它會回報「建置失敗：No available simulator runtimes」，這不是程式問題。luna 只負責寫程式與做語法層級檢查，**建置、截圖、執行驗證一律由 Claude 做**。

### 6. Claude 審查
- 看 diff，逐條對驗收條件，檢查有沒有超出範圍的改動與是否破壞既有功能。不合格就退回並說明原因，不自己動手改。結果寫入 `docs/specs/reviews/<功能名>-impl-taskN.md`，使用者說通過才 commit。
- 要看 luna 寫的、尚未套用到畫面的元件：複製專案到 scratchpad 暫存副本，把型別改成非 private、讓 App 啟動直接顯示它，建置後在模擬器截圖；**不要動原專案**。
- 淺色、深色都要看；玻璃類元件在純白背景上可能看不出來，要特別留意。
- 視覺類任務（像任務 2）完成後，先把截圖給使用者確認方向，再進下一個任務，不要等到最後的驗證任務。

### 7. 範圍與檔案
- 專案檔不進 git，新增 Swift 檔只需重新 `xcodegen generate`；不必為了避開專案檔而把所有東西塞進同一個檔案。新增檔案仍要在規格書任務清單事先列明，並限定資料夾。

## 規則

- 只讓一個 session 改程式碼；commit 只加自己這次的檔案，不用 `git add -A`。
- 不擅自 commit、不擅自升級或安裝東西。
- 換對話（`/new`）前，先把已驗證、下次會用到的內容寫進本 skill。
